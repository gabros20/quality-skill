# "What This Evidence Does Not Establish" — Worksheet

One row per tool or check. A passing check certifies only the propositions someone encoded — this
worksheet is where that boundary gets written down before the result gets reused in a dossier. Fill
new rows the same shape as the pre-filled ones. Source: `references/oracles-and-evidence.md` and the
job files named per row.

**How to fill a new row:** name the oracle first. If you cannot name what the tool is comparing
against, you cannot fill the "establishes" column honestly — stop and go find the oracle.

| Tool / check | Oracle | A pass establishes | A pass does NOT establish | Evidence class of a pass |
|---|---|---|---|---|
| **Lighthouse (performance category)** | Log-normal scoring curve + hand-set category weights, v13.4.1 (2026-07-26 pin — reverify at each Lighthouse major) | The weighted composite of the metrics it scores, on this build, this run, this network throttle profile | Anything about **INP** — Lighthouse ships INP at `weight: 0`; it is measured and displayed but contributes nothing to the score. A green score is not evidence about INP. Also not evidence about field conditions (this is lab-only) — see `performance-and-load-verification.md`. TBT alone carries weight 30, the heaviest single metric, and its own source comment calls its coefficients *"semi-arbitrarily chosen."* A score is a compressed judgment with an author, not a measurement. | `observed` for the metrics it weights, on lab conditions only; `not_tested` for INP and for field behavior |
| **Automated accessibility scanner (axe-core and similar)** | The rule's own encoded pattern-match, not WCAG itself | A bounded set of machine-detectable failure patterns is absent from this page state, this run | Full-page and full-process conformance (WCAG Conformance Requirements 2–5); anything the scanner cannot decide — **55% of axe-core's 105 documented rules can return `incomplete`/"needs review."** Automated coverage of the *overall* practical impact is a **range split by source type, never a single number**: vendor (Deque, who sells axe) self-reports **57%**; independent bodies (WebAIM, W3C/WAI, GSA) cluster at **20–33%**. The circulated 80.39% figure is unconfirmed — do not use it. axe's `impact` field is also not the same axis as WCAG conformance level — don't conflate them. | `observed` for the specific rules that ran clean; `inferred` at best for "page is accessible"; `not_tested`/`blocked` for anything the tool flagged `incomplete` |
| **Load test (e.g. k6, closed-loop generators)** | The declared workload model + the SLO/budget it's measured against | The system met the modeled workload's throughput/latency target, in this environment, for this test's duration and type (load/soak/spike/stress — whichever one you actually ran) | True tail latency, unless **coordinated omission** is corrected — a closed-loop generator sends *fewer* requests during a stall, so the worst latencies are systematically the missing samples (worked case: p99 249µs → 665ms, over 2,600× higher, once corrected). Also does not establish soak (leak), spike (burst), or stress (beyond-capacity) behavior unless that specific test type was run — a load-test pass says nothing about the other three. | `observed` for the exact scenario run; `not_tested` for every load-test type not explicitly executed |
| **Test runner "pass" verdict (Playwright / Cypress / Jest / pytest / JUnit5 / …)** | Whatever assertions the suite's author encoded — never richer than that | The encoded assertions held on this run, this commit, this environment | Anything the author didn't think to assert; and **runner verdict vocabulary is not commensurable across tools** — Playwright names a third state `flaky` (still a pass in exit-code terms); Cypress forces you to pick a policy (`detect-flake-and-pass-on-threshold` vs `detect-flake-but-always-fail`); **Jest has no flaky concept and silently reports `passed`**; pytest and JUnit5 each add distinct rerun/quarantine semantics. Never treat two tools' "green" as the same claim without checking which vocabulary each used. Also: coverage from this run measures which lines executed, not whether the *right* code exists — faults of omission are invisible to it by construction. | `observed` for the specific assertions, strictly bounded to the runner's own vocabulary for that result — always name which runner and which verdict state |
| **Mutation testing (Stryker / PIT)** | Synthetic single-line fault injection against the existing suite | The suite detects this class of synthetic simple fault, on the mutants generated this run | That the mutation *score* means anything actionable in aggregate — Google dropped the aggregate score as an operating metric because it was *"unable to be surfaced to engineers in an actionable way,"* using per-diff living-mutants instead. Equivalent mutants are undecidable, so the denominator is never exactly known. Treat mutation testing as a per-diff finding generator, not a target score to hit. | `observed` per surviving/killed mutant on this run; `not_tested`/not meaningful as an aggregate target |
| **Security scanner (SAST/DAST)** | The rule/signature set the scanner ships, run black-box or against source | No externally reachable instance of the patterns the tool encodes, at scan time | Anything at OWASP ASVS **L2 or L3** — those levels require *"documentation, architecture, source code, and the people involved"* and are **not reachable by black-box scanning at all.** Nor business logic (WSTG-BUSL) or authorization (WSTG-ATHZ) flaws, which are manual procedures by design. "We checked the OWASP Top 10" is awareness, not a verification claim — pair it with an explicit ASVS level. | `observed` for the scanned pattern set only; `not_tested` for anything requiring manual/architectural review |

| | | | | |

**Self-audit:** every row used in a dossier must have its "does NOT establish" column actually read
and copied into the dossier's evidence table (`assets/evidence-dossier.md` Part 3) — pulling only the
"establishes" column and dropping the rest is how a dossier launders a weaker evidence class into a
stronger one.
