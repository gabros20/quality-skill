## 1. Contested questions

### Q1: Pyramid, Trophy, or Honeycomb — what shape should a test suite be?

**Position A — the classic Pyramid still applies, tune the percentages.**
Origin: Mike Cohn, *Succeeding with Agile* (2010). Canonical restatement, Martin Fowler (bliki, undated, still live): "The test pyramid is a way of thinking about how different kinds of automated tests should be used to create a balanced portfolio." Ham Vocke's practitioner version (martinfowler.com/articles/practical-test-pyramid.html): "Write *lots* of small and fast *unit tests*. Write *some* more coarse-grained tests and *very few* high-level tests that test your application from end to end." Fowler explicitly flags the model's limit himself: "The pyramid is based on the assumption that broad-stack tests are expensive, slow, and brittle compared to more focused tests... If my high level tests are fast, reliable, and cheap to modify - then lower-level tests aren't needed." — i.e. even the pyramid's author says it's conditional, not a law.

**Position B — Trophy: mostly integration, JS/frontend context.**
Guillermo Rauch (@rauchg, then at Zeit/now Vercel, 711k followers, verified), 2016-12-10, verbatim, the original coinage: *"Write tests. Not too many. Mostly integration."* (https://x.com/rauchg/status/807626710350839808). Kent C. Dodds (@kentcdodds, 323k, verified) built the "Testing Trophy" model on top of it and explicitly credits Rauch every time: "'Write tests. Not too many. Mostly integration.' - @rauchg Here's my talk from @assertjs two weeks ago dissecting that statement." (2018-03-05, https://x.com/kentcdodds/status/970712783716315137). Dodds' own trophy tweet, verbatim: *"'The Testing Trophy' 🏆 A general guide for the **return on investment** 🤑 of the different forms of testing... End to end w/ @Cypress_io ⚫️ - Integration & Unit w/ @fbjest 🃏 - Static w/ @flowtype 𝙁 and @geteslint ⬣"* (2018-02-06, https://x.com/kentcdodds/status/960723172591992832). His canonical blog (kentcdodds.com/blog/write-tests) adds the falsifiable number missing from the tweets: coverage delivers "diminishing returns... beyond 70%," and his guiding heuristic is "The more your tests resemble the way your software is used, the more confidence they can give you." Gergely Orosz (@GergelyOrosz, 345k, verified) later documented the phrase's canonization: "How a good idea goes from a tweet, to a blog post, to part of a hardcover book... A tweet by @rauchg, a visualization and blog by @kentcdodds: made it into The Software Engineer's Gudiebbok" (2025-11-01).

**Position C — Honeycomb: microservices need a fat integration middle.**
Spotify Engineering (2018, engineering.atspotify.com/2018/01/testing-of-microservices, confirmed by direct fetch): "The biggest complexity in a Microservice is not within the service itself, but in how it interacts with others," so "having too many unit tests in Microservices... restricts how we can change the code without also having to change the tests." Their honeycomb: fat integration middle, thin unit base, thin (ideally empty) full-system top. Circulated on X by Yan Cui (@theburningmonk, self-described "24k followers, unverified badge but well-known AWS serverless author"), 2023-08-28: "why it's time to say goodbye to the test pyramid and welcome the 𝘁𝗲𝘀𝘁 𝗵𝗼𝗻𝗲𝘆𝗰𝗼𝗺𝗯!" — and summarized by @swyx (176k, verified), 2020-05-15: "The @MartinFowler Test Pyramid has fallen out of style... In frontend, we now have the 'Testing Trophy' from @rauchg and @kentcdodds. In backend, @theburningmonk's course advocates the 'Testing Honeycomb' from @SpotifyEng."

**What decides it:** deployment topology, not taste. Single-process monoliths (DHH's "majestic monolith" position, below) tolerate a classic pyramid because unit tests cheaply exercise real code paths. Distributed systems (Spotify's case, and @arpit_bhayani's 2026-07-15 post below) make unit tests cheap-but-blind to the actual risk (service interaction) — hence honeycomb/trophy-style resource shifts toward the middle. Modern .NET engineer @mjovanovictech (49k, verified) makes the same call for a different reason — tooling, not topology — 2026-05-11: "The test pyramid was good advice for 2009... Back then, integration tests were expensive... But the economics changed. With Testcontainers, I can spin up PostgreSQL, Redis, and RabbitMQ in seconds... A thin layer of unit tests for pure domain logic. A thick middle of integration tests against real infrastructure. A few critical end-to-end tests." — the same "un-pyramid" conclusion reached independently, dated to *tooling cost curves* rather than architecture.

### Q2: Are E2E tests a trap or the only tests that actually matter?

**Position A — E2E is a liability at scale; kill the shared environment.**
Arpit Bhayani (@arpit_bhayani, 124k, verified, system-design educator), 2026-07-15, verbatim, the single strongest falsifiable claim in the whole sweep: *"End-to-end tests do not work at scale, nor does staging infrastructure. Past a certain number of services, both turn into a liability... A shared database, shared services, and everything around them all need to be up, on the right version, and in the right state at the same time... One flaky service and the whole suite goes red, for a reason that has nothing to do with the code being tested... What works instead is each service owning its own tests and mocking the responses of the services it depends on... Cross-service behavior gets verified through contract tests between two teams, not through a shared environment that everyone touches and no one owns."* (https://x.com/arpit_bhayani/status/2077381342376104097). Amplication's official account, 2023-02-22: "Automation for end-to-end test cases should be minimized since implementing and maintaining these is more costly when compared to other level tests."

**Position B — E2E/use-case coverage is what actually catches production breakage.**
David Khourshid (@DavidKPiano, creator of XState, 87.9k, verified), 2022-08-27, verbatim: *"Use-case coverage is far more important than code coverage. You can have 100% code coverage and still have your app break in prod. Use cases can be encoded in end-to-end (E2E) tests, which will produce tests that are as close as possible to how an app will actually be used."* DHH (@dhh, 764k, verified) makes a related but distinct claim for *manual* E2E — exploratory testing, not automated — see Q6 below.

**What decides it:** whether "E2E" means "automated browser/API flow within one deployable" (cheap, valuable, keep it) or "automated flow across N independently-deployed services via a shared staging environment" (expensive, fragile, the thing Bhayani is attacking). The two camps are often talking past each other because they use "E2E" for different things — exactly the ambiguity Fowler warns about in his bliki ("teams often conflate the concepts of end-to-end tests, UI tests, and customer facing tests... orthogonal characteristics").

### Q3: Flaky tests — quarantine, delete, or fix? Is auto-retry a sin?

**Position A — flakiness is a symptom; fix the root cause, don't hide it.**
Cory House (@housecor, 161k, verified), 2023-11-17, verbatim thread: *"I've worked with teams that were scarred by their previous automated testing experience... So flaky tests don't necessarily mean the tests are bad. Sometimes flaky tests merely shine a spotlight on existing issues. Adding tests to a flaky app leads to flaky tests. Solution? Fix the root cause of the flake."* Sam Saffron / Discourse (samsaffron.com/archive/2019/05/15/tests-that-sometimes-fail, fetched directly), citing Fowler: *"Non-deterministic tests have two problems, firstly they are useless, secondly they are a virulent infection that can completely ruin your entire test suite."* Discourse's actual policy, verbatim from the post: *"Quarantine and fix"* — skip flaky tests temporarily but keep them visibly skipped so they don't get forgotten, paired with "If the build is not green nothing gets deployed."

**Position B — auto-retry as pragmatic triage at scale, not sin.**
Uber's Testopedia (described by @gkcs_, 71.8k, verified, 2024-12-08): *"If a test is flaky (passes sometimes and fails sometimes), mark it for analysis and ignore its result... Critical tests run regardless of flakiness. Developers are allowed to switch flaky tests ON or OFF for every PR. Flaky tests can be run asynchronously in non-blocking mode."* At 10,000+ tests on some critical PRs and 2,500+ PRs/day, Uber's stated tradeoff is explicit: accept "lesser test coverage" in exchange for a CI signal developers can trust. Vitest 4.1 shipped "Enhanced retry options for flaky tests" as a first-class feature (@voidzerodev, 2026-01-21) — tooling now treats retry as normal infrastructure, not a hack.

**Position C — flaky tests are simply worse than no tests.**
Aaron Patterson [UNVERIFIED handle status — see §5] (@tenderlove, 2019-08-30): *"Flaky tests are worse than useless tests."* @techNmak (40.8k, verified), summarizing consensus, 2025-02-21: "Flaky tests worse than no tests."

**What decides it:** organizational scale. Below ~hundreds of tests, House/Saffron's "find and fix the root cause" is tractable and is the discipline you want. Above Uber-scale (thousands of engineers, tens of thousands of tests/day), a fully manual "fix every flake" policy doesn't survive contact with reality, so quarantine-with-a-tracking-system and PR-level toggles become the pragmatic middle path — not because flakiness stopped mattering, but because a red-everything CI is a worse outcome than a slightly-leaky one. The empirical baseline everyone cites: John Micco/Google reported (secondhand, via a comment on Saffron's post — flag as once-removed) "almost 16% of our tests have some level of flakiness," and a commenter on the same post: "I used to work at a company with over 10,000 tests where we weren't able to get more than an 80% pass rate due to flaky tests" (circulated by @codinghorror, 262k, verified, 2019-06-03).

### Q4: Is 100% coverage worth chasing? (Goodhart's Law in testing)

**Position A — coverage percentage is a proxy that gets gamed; don't reward the number.**
Milan Milanovic (@milan_milanovic, 62.9k, verified), 2026-06-02, the sharpest and most concrete Goodhart's-Law post in the sweep, verbatim: *"Deleting 1,500 lines of code marked one of my best engineers as a low performer... Reward coverage percentage, and you get trivial tests that assert nothing, while the hard integration tests stay unwritten... Before you attach a reward to a number, ask one question: could gaming it leave you worse off than measuring nothing at all?"* (attributes the "measure becomes a target" line to Marilyn Strathern, paraphrasing economist Charles Goodhart). Cory House, 2022-10-06: *"Code coverage can lie. 100% coverage doesn't mean all code is covered. One solution: Mutation testing... mutation testing tests... the tests!"* Kent C. Dodds' blog: diminishing returns "beyond 70%" coverage.

**Position B — coverage is still the right forcing function, especially now that AI writes the code.**
Uncle Bob / Robert C. Martin (@unclebobmartin, 254k, verified), 2026-03-21, on why coverage is necessary but not sufficient in the AI-agent era, verbatim: *"So you have to run test coverage and direct the AI to cover all the uncovered lines. That will stabilize the shape of the container; but it leaves holes. Remember that coverage does not prove that the tests cover everything with assertions, it only proves that the tests execute the covered lines. Those holes are leaks that the AI can sneak through -- and it will."* His conclusion is not "abandon coverage" but "coverage plus mutation testing" (see Q5) — coverage is the floor, mutation testing is what plugs the Goodhart gap.

**What decides it:** whether coverage is used as a target (gameable, Milanovic's warning) or a diagnostic floor combined with a second, harder-to-game signal (mutation score) — Martin's actual 2026 practice is "coverage AND mutation," not "coverage instead of mutation." The 60–80% coverage target repeated across several `milan_milanovic` posts is itself somewhat circulating folklore rather than a rigorously sourced number — treat as a widely-repeated heuristic, not an empirical finding.

### Q5: Why did mutation testing never go mainstream, and is that changing?

**Position A — historically impractical (compute cost), now unlocked by AI agent labor.**
Uncle Bob, 2026-03-12, verbatim: *"Why don't most programmers know about mutation testing? Because it was virtually impractical to use. Now it's not."* And 2026-02-26: *"I always thought that mutation testing was a good idea; but it was always hard to afford. Now it's just one more Claude agent working down a list. And the benefit is amazing."* He backs this with an actual cost-engineering trick — differential mutation testing — 2026-05-19, verbatim: *"There is no point in mutation testing a function that has not been changed since its last mutation test. So I have the tool create a manifest in a comment at the end of each module... Only those functions whose hash codes don't match are mutated. This can save a ton of computer and clock time."* And a real empirical comparison across languages (2026-06-02): a three-language experiment (Java, Clojure, Go) running the same spec through agent swarms doing coverage+crap+mutation testing found "Java: 5+ hours... Go: 3:29... The CPU usage was driven primarily by mutation testing... I presume the Java run was slowed down by at least two extra hours of compute bound time" — i.e. mutation testing's CPU cost is still the dominant cost driver even with agents doing the labor, it's just now affordable.

**Position B — PHP/JS ecosystems still treat it as a niche feature, adoption is grass-roots.**
Enunomaduro/Pest PHP (66.9k, verified) shipped mutation testing as a Pest v3 headline feature in 2024 specifically *because* it wasn't already standard: gehrisandro (2023-10-30, building the Pest mutation plugin): *"In the PHP ecosystem, Mutation Testing is not widely used so far, mainly because developers don't know about it or it's too hard to start with."* Alex Bunardzic, 2023-07-09: *"How is it possible to be a software developer and to have never heard of mutation testing?"* — a complaint, not a description of dominance.

**What decides it:** cost. Both positions agree on the mechanism (mutation testing is valuable, historically too slow/expensive to run on every commit); they disagree only on whether 2026-era compute (cheap agent labor, differential/incremental mutation) has actually crossed the threshold to make it standard practice, or whether it remains a tool a motivated minority reaches for. The sweep has real signal for the former (Uncle Bob's concrete workflow) and mostly promotional/vendor tweets for the latter (Pest, PhpStorm, Stryker) — not enough independent, non-vendor-tied testimony to call it "mainstream" yet as of 2026-07.

### Q6: Exploratory testing vs automation — is manual testing dead?

**Position A — exploratory testing is a distinct, irreplaceable discipline (testing ≠ checking).**
Michael Bolton, developsense.com/blog/2009/08/testing-vs-checking (fetched directly), the canonical formulation: *"Testing is something that we do with the motivation of finding new information... Checking is something that we do with the motivation of confirming existing beliefs... A check provides a binary result—true or false, yes or no"* — the deciding variable is *sapience*: "If it requires a human, it's a sapient process, and is far more likely to be testing." Martin Fowler's bliki (ExploratoryTesting.html, referenced by his own tweet, 2019-11-18): "I'm a strong proponent of extensive automated testing, but there is still an essential role for Exploratory Testing." Dave Farley (@davefarley77, unverified badge but well-known author of *Continuous Delivery*, 2019-04-04): *"Let's use Humans for what they are good at: Fuzzy pattern matching, intelligent analysis. Let's use machines for what they are good at: Fast repeatable results for 10's, or 100's, of thousands of tests."*

**Position B — DHH: automation augments, it doesn't replace human testers; a team with no exploratory testing at all is a red flag.**
DHH (@dhh, 764k, verified), quoting/endorsing his own Basecamp blog post (signalvnoise.com, fetched directly — author confirmed DHH, posted 2017-11-09), verbatim: *"Automated testing does not replace 'testing by hand', it augments it... Testing by hand, or exploratory testing, is a crucial technique for ferreting out issues off the happy path. It is best carried out by dedicated testers who do not work on implementation."* And separately, 2019-11-22, quoting the same Fowler bliki piece approvingly: *"'I would consider it a red flag if a team isn't doing exploratory testing at all - even if their automated testing was excellent', amen!"*

**Tension inside the automation camp:** whether automators and exploratory testers should be organizationally separate. Carlos Kidman, 2021-06-04, pushing back on a claim from a training class: *"'Automators should be doing automation and not exploratory testing' ... I couldn't disagree more. I hoped this 'us vs them' stuff was old news, but it seems more common amongst testers."* The Friendly Tester (@FriendlyTester, unverified, well-known RST-adjacent tester-educator), 2023-07-08: *"Your team cannot create valuable automated tests/checks without exploratory testing. You need to explore a system, to understand it enough to create valuable automation."*

**Skeptical outlier worth recording:** Allen Holub (@allenholub, unverified, well-known OO/agile author), 2021-10-10, a genuinely open question rather than a settled dismissal: *"Would one of the exploratory testing folks explain to me how uncovering a bug that doesn't impact an end user's work in any way is useful? I'm trying to understand what's worth the time and money and what isn't."* — nobody in the sweep answers him directly; record as a live, unresolved objection rather than resolve it for him.

**What decides it:** whether the org treats "testing" and "checking" as the same activity. Everyone quoted agrees automation ("checking") is necessary; the live disagreement is whether human exploratory testing is (a) essential and irreplaceable (Bolton, DHH, Fowler, Farley, FriendlyTester) or (b) a nice-to-have whose ROI needs justifying case-by-case (Holub's implicit position). No one in the sweep argues exploratory testing should be *eliminated* — the debate is about proportion and staffing, not existence.

### Q7: TDD — dead, alive, or was the 2014 debate about the wrong thing?

**Position A — DHH's 2014 break, still cited as the founding "TDD is dead" text.**
DHH (@dhh), 2014-04-23, the actual origin tweet, verbatim: *"TDD is dead. Long live testing: http://t.co/1hHOG2SV46"* (https://x.com/dhh/status/458928132527902720). Per Martin Fowler's summary page (martinfowler.com/articles/is-tdd-dead/, fetched directly) of the resulting three-way video series with Kent Beck and Fowler himself, DHH's three objections were: (1) TDD gets conflated with "self-testing code" and unit testing generally; (2) heavy mocking under strict TDD produces "test-induced design damage" — unnecessary indirection (hexagonal-architecture-style layering) forced by testability concerns rather than actual design need; (3) the red/green/refactor cycle simply didn't fit his own workflow. The panel's actual resolution, per Fowler's own summary quote: *"you have to build up what practices work for you and your team, you can't take any technique blindly."* — i.e. the "TDD is dead" framing oversold what was actually a "TDD isn't universal" conclusion that all three panelists could accept.

**Position B — by 2025/2026, TDD is more widely practiced than ever; "X is dead" claims don't age well.**
Takuto Wada / t_wada (@t_wada, well-known Japanese TDD advocate, unverified badge — see §5), 2026-02-26, verbatim (Japanese): *"2014年に『TDD is Dead』と言われるも2025年はTDDがこれまでで一番普及した年になったので、XXXis Deadなんてそんなもんです。"* (translation: "Even though 'TDD is Dead' was declared in 2014, 2025 turned out to be the most widespread year for TDD ever — that's just how 'XXX is Dead' claims go.") This is the single most pointed piece of evidence in the sweep that the "TDD is dead" narrative did not hold up over a 10+ year horizon, from a practitioner specifically identified with TDD advocacy in the Japanese dev community.

**Position C — TDD's actual mechanism was never about test-first ordering.**
Uncle Bob's 2016 blog "TDD Doesn't Work" (blog.cleancoder.com, fetched directly) makes a claim that complicates *both* sides: responding to a study claiming TDD showed no benefit, he argues the study's real finding undermines its own framing — *"The really effective part of TDD is the size of the cycle, not so much whether you write the test first... The reason we write the tests first is that it encourages us to keep the cycles really short."* This reframes the entire "is TDD dead" argument as a category error: the debate over test-first-vs-test-last was answered by a study that (per Martin) actually validated short-cycle discipline, which both TDD and disciplined TLD share.

**Practitioner texture, 2026, post-AI-agent era:** Cory House, 2023-11-20, on why he personally skips TDD: *"TDD commits me to an API before I know what API I want. At first, I'm just iterating. Once I like the API, I add tests."* James Shore (@jamesshore, well-known agile/XP author, unverified), 2020-10-02: *"TDD doesn't mean 'write the tests, then write the code.' It means 'write A SMALL PART of the tests, write A SMALL PART of the code.' (Then reflect, improve, and repeat.)"* Matt Pocock (@mattpocockuk, 315k, verified), on AI-agent-driven TDD specifically, 2026-05-21: *"Adding a tweak to the /tdd skill: 'Do not add tests which simply restate the implementation. These provide zero confidence.' Getting sick of shit tests just to provide evidence of RGR."* — a live, current (2026) complaint that AI coding agents doing TDD mechanically produce tautological tests that satisfy the ritual without the substance — echoing DHH's "test-induced damage" concern in a new form twelve years later.

**What decides it:** definitional discipline. Every credible voice in this thread — DHH, Beck, Fowler, Uncle Bob, t_wada, House, Shore — converges on "strict test-first-always is not universally required; disciplined short feedback loops are." The genuine, unresolved fight is only about whether "TDD" as a *label* should still mean the strict ritual or the underlying discipline — which is why the 2014 debate keeps getting re-litigated instead of resolving.

### Q8: Is QA as a role being eliminated, absorbed into dev, or becoming more valuable?

**Position A — QA absorbed into engineering is a mistake if it's just "cut the team."**
Iba Marief (@ibamarief, 20.8k, verified), 2023-08-23, the single substantive long-form QA-org thread in the sweep, verbatim on the trap: *"having overreliance on manual testing and positioning their QA as manual testers instead of investing in building test automation... The result is that QA teams provide increasingly lower value to the company. Lower value to the company = lower salary. Increasingly lower value = dead-end job... Last month, I heard one local tech startup even skipped the QA process altogether and disbanded its entire QA team."* His prescription is not "eliminate QA" but "reposition QA as Quality *Analysts*, not Quality *Assurance*" — shift-left into the design phase, doing failure-path analysis before code exists, rather than end-of-pipeline gatekeeping: *"this is the third mistake for many tech companies: treating their QA roles as Quality Assurance instead of Quality Analysts."*

**Position B (weak signal, mostly vendor-driven) — AI test-generation tools are marketed explicitly as QA-role replacement.**
A side-project post (@haider__anis, 2026-02-17) captures the sentiment even though it's a product testimonial, worth recording as *cultural* evidence rather than an authoritative claim: *"Let's just say some traditional testing roles should probably be updating their résumés."* Modern Testing's own 7th principle (moderntesting.org, fetched directly) states the absorption thesis as an explicit organizational goal rather than a threat: *"We expand testing abilities and knowhow across the team; understanding that this may reduce (or eliminate) the need for a dedicated testing specialist."*

**What decides it:** whether "QA" is defined as manual regression execution (genuinely being automated away) or as the analytical/design-phase discipline Marief and Modern Testing both point toward (increasingly valuable, differently titled). The sweep has real, first-hand practitioner evidence for the "manual-execution QA is shrinking" claim and the "shift QA earlier and it becomes more valuable" prescription — both from the same thread, not opposing camps.

## 2. Settled / consensus

Claims that no credible practitioner in the sweep contests, stated with specific evidence:

- **100% coverage is not a meaningful target, and everyone quoting a number lands in the 60–80% range or says "don't chase 100."** Independently stated by Kent C. Dodds (blog: diminishing returns past 70%), Milan Milanovic (multiple posts: "our goal shouldn't be 100% test coverage"), Cory House ("100% coverage doesn't mean all code is covered"), and Uncle Bob ("coverage does not prove that the tests cover everything with assertions, it only proves that the tests execute the covered lines"). No pro-100%-coverage voice appears anywhere in the sweep.
- **Flaky tests are a serious, not cosmetic, problem, and letting them rot destroys trust in CI.** Universal across Discourse/Saffron, Uber/Testopedia, House, tenderlove, Google (16% flakiness figure), and the Gradle/Develocity "seven reasons" post. The only live disagreement is remediation policy (fix vs quarantine vs retry), not whether it matters.
- **Automated tests ("checking," per Bolton) and human exploratory testing are complementary, not competing.** Bolton, Fowler, DHH, Farley, and FriendlyTester all state this explicitly with no dissent found — including from DHH, whose other positions (majestic monolith, TDD skepticism) are otherwise contrarian.
- **"Write tests. Not too many. Mostly integration." is attributed, without dispute anywhere in the sweep, to Guillermo Rauch (2016), popularized and elaborated by Kent C. Dodds.** Dodds himself never claims authorship; he cites Rauch every time. The only friction is people mis-citing it as blanket permission to skip unit tests (kossnocorp's complaint, §4).
- **A single-process/monolith architecture makes unit-test-heavy pyramids more viable; a distributed/microservices architecture makes integration-heavy honeycomb/trophy shapes more viable.** This is effectively the resolution of Q1 — nobody in the sweep argues one shape is universally correct across both architectures.
- **Mutation testing is a good idea whose historical bottleneck was compute cost, not conceptual disagreement.** No one argues mutation testing measures the wrong thing; the debate (Q5) is entirely about cost/practicality, and that debate is visibly shifting in 2026 due to AI-agent compute.

## 4. Practitioner heuristics

Rules of thumb, attributed where the sweep supports it, that are more specific/falsifiable than textbook material:

- **"If your unit-to-E2E test ratio isn't at least 10:1, something is off."** — @milan_milanovic, 2026-04-23.
- **"If a bug can be caught by a unit test, don't write an E2E test for it. Push tests down."** — @milan_milanovic, same post.
- **"Adding tests to a flaky app leads to flaky tests. Fix the root cause of the flake, not the test."** — @housecor, 2023-11-17.
- **"If the build is not green, nothing gets deployed"** — used as an organizational forcing function to prevent flaky-test rot (Discourse/Saffron), not just a CI setting.
- **Quarantine flaky tests visibly (skip-with-a-tracking-mechanism) rather than deleting them or leaving them red** — Discourse's stated policy, contrasted explicitly against "delete" and "run until passing" as options they rejected.
- **Only mutate/retest functions whose source hash has changed since the last mutation run ("differential mutation testing")** — Uncle Bob, 2026-05-19; a concrete cost-control technique not found in older mutation-testing literature circulated pre-2025.
- **"Do not add tests which simply restate the implementation" as an explicit rule fed to an AI coding agent's TDD workflow, because agents doing red-green-refactor mechanically will produce tautological tests otherwise.** — @mattpocockuk, 2026-05-21. This is a genuinely new (2026) heuristic responding to a genuinely new failure mode (AI-driven TDD ritualism).
- **TDD's real value is cycle-length discipline, not test-order** — meaning teams that do disciplined test-last-in-small-batches get most of TDD's benefit; the "write the test first" ritual is a forcing function for short cycles, not the mechanism of benefit itself. — Uncle Bob, 2016 (blog.cleancoder.com).
- **A mocked integration test doesn't prove the mock matches reality — treat contract mismatches as a two-team problem, not a code-review problem.** — @arpit_bhayani, 2026-07-15; @hwisesa23, 2026-07-26 ("A mocked integration doesn't prove it matches reality").
- **Ask "could gaming this metric leave us worse off than measuring nothing?" before attaching a reward to any test/quality metric.** — @milan_milanovic's practical Goodhart's-Law test, 2026-06-02.
- **Reposition QA from end-of-pipeline gatekeeping to pre-code failure-path analysis during design ("Quality Analyst," not "Quality Assurance") to escape the "QA = dead-end job" trap.** — @ibamarief, 2023-08-23.
